## 问题清单（13项）

### 严重（1项）

| # | 问题 | 位置 | 说明 |
|---|------|------|------|
| 1 | **sqlite-vec migration v4 崩溃风险** | `sqlite.ts:initDatabase` + `runMigrations` | `initDatabase` 先加载 sqlite-vec 扩展再返回 Database 对象。扩展加载失败时 `vecEnabled` 为 false，但 `runMigrations` 不检查该标志，v4 仍会执行 `CREATE VIRTUAL TABLE ... USING vec0(...)`，SQLite 直接报 "no such module: vec0"。虽有 try-catch 但会抛异常中断整个迁移流程，导致 `add_notifications`（v6）、`temporal_graph_fields`（v8）等后续迁移全部不执行。即使扩展加载成功也存在竞态：v4 的 `IF NOT EXISTS` 只在表不存在时创建，若 vec0 模块正常但表创建因其他原因失败，不会重试。 |

### 中等（7项）

| # | 问题 | 位置 | 说明 |
|---|------|------|------|
| 2 | **CoreMemory LRU 淘汰策略错误** | `core-memory.ts:409` | `updateCache` 满时淘汰策略是 `this.cache.keys().next().value`，按 JS Map 的插入顺序而非访问顺序淘汰。`get()` 命中缓存时只更新了 `accessCount`/`lastAccessed`（第83-84行），没有调用 `updateCache` 执行 `delete+set` 来刷新 Map 迭代顺序。结果：最早插入的高频热数据会被错误淘汰，而刚插入的冷数据留在缓存中。 |
| 3 | **vec_entities 维度硬编码 384** | `sqlite.ts:139` | migration v4 的 `embedding FLOAT[384]` 硬编码。`embedding/service.ts` 虽已支持动态维度，但 vec0 表结构不变。若用户使用 768/1024/1536 维的模型，向量写入 vec0 时维度不匹配，整列写入失败，KNN 搜索不可用。 |
| 4 | **FTS5 查询未转义** | `sqlite.ts:438-442` | `searchEntities` 直接将用户输入传给 `fts_entities MATCH ?`。FTS5 MATCH 语法中 `-` `(` `)` `"` `*` `AND` `OR` `NOT` 等有特殊含义。搜"AI-driven projects"会被解析为 `AI` 与 `NOT driven` 与 `projects` 的逻辑组合。虽会 catch 异常回退到 LIKE，但这意味着每次搜索含特殊字符时 FTS5 必然失败。 |
| 5 | **decay-scheduler 事务内逐条 UPDATE** | `decay-scheduler.ts:227-231` | `_decayRelationships` 在 `withTransaction` 内对 `updates` 逐条 `UPDATE`。虽是批量事务但仍是 N 次独立 SQL。当需要衰减上万条关系时，N 次 fsync+round-trip 开销大。可用一条 `CASE WHEN` 批量 UPDATE 替代。 |
| 6 | **LLM 调用无重试机制** | `llm-pipeline.ts:140`、`conflict-resolver.ts:128`、`mcp.ts:148` | 三处 LLM 调用均无重试。LLM API 临时不可用时（429 限流、网络抖动、502）直接返回空结果/抛出异常。LLM 提取管道的 `extract` 返回 `_emptyResult()` 静默丢失语义提取层；`callLlmDecision` 返回空分析；`resolveConflicts` 跳过该组冲突。 |
| 7 | **OCR 每次 new + dispose** | `extractor.ts:451-467` | `combineInputs` 每次截图都 `new OCRPipeline()` 然后 `await ocr.dispose()`。虽然 `OCRPipeline` 类支持复用（有内部 worker 管理），但调用方不复用。每次 new 意味着重新初始化 Tesseract worker（加载 wasm/语言包），高频率截图提取时浪费严重。 |
| 8 | **searchEntities handler 全量加载再 JS 过滤** | `mcp.ts:281-287` | 当 MCP 调用 `search_entities` 并指定 `type` 时，handler 先调用 `getEntitiesByType(type)` 拉取该类型所有实体到内存，再用 JS `.filter()` 做关键词匹配 + `.slice(limit)`。若某类型有数千实体，每次都全量拉取。而数据库层 `searchEntities` 已支持 FTS5/LIKE 混合搜索，完全可以在 SQL 层同时做类型过滤。 |

### 低（5项）

| # | 问题 | 位置 | 说明 |
|---|------|------|------|
| 9 | **向量搜索回退内存风险** | `sqlite.ts:841-857` | `_vectorSearchFallback` 一次性 `SELECT ... FROM entities WHERE embedding IS NOT NULL` 加载所有带向量的实体到 JS 内存做余弦相似度计算。实体过万时内存占用可达数百 MB。 |
| 10 | **VALID_ENTITY_TYPES 缺少 'decision'** | `extractor.ts:235-247` | `VALID_ENTITY_TYPES` Set 包含 13 个类型，但 `shared-types.ts` 的 `EntityType` 联合类型有 14 个（多了 `'decision'`）。LLM 若返回 `type: "decision"` 的实体会被白名单过滤降级为 `"concept"`，且 `originalType` 记录进 metadata。虽然 `save_decision` handler 走另一路径创建决策实体不经过此白名单，但如果 LLM 提取阶段产出决策类型实体会静默变形。 |
| 11 | **关系查询 OR 条件索引利用差** | `sqlite.ts:693-694` | `getRelationshipsForEntity` 的 `WHERE (source_id = ? OR target_id = ?)` 会阻止 SQLite 优化器有效使用 `idx_relationships_source`/`idx_relationships_target` 索引，在关系数大的实体上可能触发全表扫描。可用 UNION 替代 OR。 |
| 12 | **FTS5 同步异常信息不详细** | `sqlite.ts:939-940` | `_syncFtsEntity` 的 catch 只 `console.warn` 不记录 err 本身。若 FTS5 表损坏或 tokenizer 不可用，无法从日志定位具体原因。 |
| 13 | **conflict-resolver 无并发控制** | `conflict-resolver.ts:32-186` | `resolveConflicts` 对每对新关系串行发起 LLM 调用。若一次 extraction 产出 20 条新关系且均有冲突，需要串行 20 次 LLM 调用（每次最多 15s），总耗时可能数分钟。同时每条关系处理中无单独的错误隔离和超时兜底，前一条卡住会影响后面全部。 |
**一个小建议：** `analyze_decision` 和 `discuss_decision` 目前只在 HTTP API 层实现，还没加到 MCP stdio server 里。如果你想让 Claude Desktop / Cursor 用户也能用决策助手，需要把这两个工具也同步到 `mcp-server.ts` 中。
