## Request determinism

**Verdict: DETERMINISTIC_FROM_FIXTURE_AND_ARM**

- Provider-visible payload = pure function of (fixture sample, armId, frozen prompt files, frozen `confirmed_parameters`). Fields checked: URL, method, headers (Content-Type, Authorization only), `model`, `messages[0..1]`, `temperature`, `max_tokens` (65536), `stream`, `response_format`, `thinking`, `reasoning_effort`, `top_p` (omitted). No user/id/request-id/cookie/session field exists.
- Response format / JSON schema / prompt do **not** vary by tuple index; `output-schema.json` is identical across arms (2196 bytes each) and re-read per tuple.
- Retry policy does **not** change request bytes between attempts (deterministic re-render; byte-identity asserted in `executor.test.mjs:595-601, 650-653` and re-verified empirically).
- Empirical check: 5 fresh renders of A3/tt15-006 produced byte-identical 9282-byte bodies, sha256 `03b12ee6100231e3…`; the body contains no `711`/`tt15`/`attempt`/`tuple_index` tokens.

## Tuple-index dependence

**Found: false.** `tuple_index` appears only in storage keys, ledger records, and test-injection keys — never in the provider-visible request. The frozen execution order places tuple 711 at position **284** (not 711), so failures follow the tuple identity, not the loop position. The only tuple-dependent runtime effect is retry-backoff stagger (timing only).

## Verdict

**`state_leak_defect_found: false`.** No executor state that depends on call index or run progress can cause or correlate with the tuple-711 EMPTY_CONTENT failures. The provider-visible request is a pure function of (fixture sample, armId, frozen prompt files, frozen confirmed parameters): the request body has no tuple-index/attempt/run-progress field, retries reuse byte-identical bodies (asserted by tests and re-verified empirically - 5 renders of A3/tt15-006 produced identical sha256 03b12ee6100231e3...), every AbortController/timer/schema/parser object is per-call, the only mutable run-progress state is the budget ledger (which can only stop the run with BUDGET_HARD_CAP_EXCEEDED, never produce an empty 200), and no literal special-casing of '711'/'tt15'/'A3' exists anywhere. Consistent with this, the failures follow the tuple identity (which executes at order position 284, not 711) across runs. The observed 3x/4x/5x EMPTY_CONTENT patterns are exactly the frozen per-class attempt budgets (3 default / 5 EMPTY_CONTENT / 6 transport) applied uniformly to all tuples, and the repeated emptiness of this specific tuple's requests is therefore attributable to provider-side behavior on this specific frozen request content, not to executor state. Audit scope: read-only source review; no executor run and no provider calls were made.
